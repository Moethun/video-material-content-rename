# 实测记录与踩坑总结

[English](FINDINGS.md) | 中文

这份文档记录的是**真实跑过的数据**，不是理论估计。所有结论都来自一次完整项目：
一次旅拍 vlog 拍摄，286 个实拍片段，1080p，单个 2-45 秒，合计 10.59 GB，全部为相机机内麦录制的
`pcm_s16be` 音轨。

写出来的目的是：让你跳过我们踩过的坑。

---

## 一、素材本身的坑

### 1.1 文件大小完全不能用来判重

侦察阶段发现大量文件字节数一模一样：

```
29365858 字节  ×  40 个文件
25171314 字节  ×  36 个文件
```

第一反应是"这批素材有大量重复"。**但做完全量 MD5 后，286 个文件哈希全部唯一，零重复。**

原因是同一台相机、同一参数连续拍摄时，编码器输出的文件长度会高度一致，内容却完全不同。
按大小判重会直接删掉几十条真实素材。

**结论：查重必须全量哈希。** 10.59 GB 的 MD5 计算在这个量级是分钟级的，成本可以接受。

### 1.2 时长跨度大，不能用一种策略处理

```
min 1.92s   avg 5.85s   max 45.12s   合计 27.9 分钟
```

2 秒和 45 秒的片段放在一起，抽帧策略、转写策略都要分开考虑。这也是后来引入
"时长预筛"的原因（见 §3.2）。

## 二、Whisper 的坑

### 2.1 `initial_prompt` 会被当成内容复读

最初的想法很直觉：喂一段领域引导词，比如 `"以下是一段城市生活 vlog 的普通话旁白。"`，
能让模型输出更贴合的词汇，改善专有名词。

**实际结果：这个 prompt 被原样吐了出来。**

```
街拍空镜_01.MP4      →  "OK,城市,生活vlog的普通话旁白。"     ← prompt 变体
博主口播_01.MP4      →  "这次是城市生活vlog的普通话旁白。"    ← prompt 变体
咖啡拉花_01.MP4      →  "这段是城市生活vlog的普通话旁白。"    ← prompt 变体
天际线日落_01.MP4    →  "这位置是城市生活vlog的普通话旁白。"  ← prompt 变体
```

当音频里没有清晰语音时，模型会用 prompt 补全出一个"看起来合理"的句子。
这比输出空字符串糟糕得多——空的你可以识别，这种看起来像正常结果的幻觉会污染整批数据。

**结论：`initial_prompt=None`，永远不传。**
专有名词的问题用**事后术语纠错表**解决，比事前引导干净得多。

### 2.2 短音频的重复幻觉

用 tiny 模型时，短片段会陷入单句循环：

```
"其中一段時間我已經準備了一段時間了我已經準備了一段時間了我已經準備了一段時間了"
"請問是有点有点有点有点有点有点有点有点有点有点有点...（重复上百次）"
```

`condition_on_previous_text=False` 能显著缓解，但模型太小的话仍然会出现。

后处理层面用正则折叠连续重复单元：

```python
text = re.sub(r"(.{2,6}?)\1{3,}", r"\1", text)
```

### 2.3 中文简繁输出不稳定

同一条结果里出现简繁混排：

```
"这段素材不是按一下按鈕就完事為什麼畫面會抖動使用什麼穩定器怎麼拍出实物感"
         ~~~~ ~~~~ ~~~~~~ ~~~ ~~~ ~~
```

**结论：必须用 `zhconv.convert(text, "zh-cn")` 统一，再做术语纠错。**
注意顺序——先转简体再纠错，否则繁体形态的词会漏掉。

### 2.4 同音错字（人名 / 地名重灾区）

一个两字的人名，在 286 条素材里被听成了 **8 种不同写法**：

```
林许 / 林绪 / 临序 / 淋序 / 林絮 / 邻序 / 林旭 / 凌序      （正确：林序）
```

其他典型错法：

| 错法类型 | 例子 |
|---|---|
| 英文 App / 设备名 | 被按发音拼成中文，或拼错一两个字母（`StreamLab` → `StreamLap`） |
| 常见词吞音 | 脑海 → 能害 ｜ 名额 → 名革 ｜ 网红打卡 → 网宏打卡 |
| 专业词混淆 | 调色预设 → 调色预舍 ｜ 实物 → 食物 |

**结论：术语纠错表是必需品，不是可选项。** 攒法见 `examples/terms.example.tsv`。

顺带一提：名字越短越容易错，而恰好名字又是最不能错的部分——
一条素材讲的是谁、在哪儿，全靠这几个字。

## 三、参数与策略结论

### 3.1 最终参数组合

```python
model.transcribe(
    audio_array,
    language="zh",
    beam_size=5,
    initial_prompt=None,               # 关键：传了会被复读
    condition_on_previous_text=False,  # 关键：否则短音频陷入重复循环
    vad_filter=True,
    vad_parameters=dict(min_silence_duration_ms=500),
    no_speech_threshold=0.6,
    log_prob_threshold=-1.0,
    compression_ratio_threshold=2.4,
    temperature=[0.0, 0.2, 0.4],
)
```

后三个阈值 + temperature 序列是一组抑制幻觉的联合参数，缺一个都会漏出垃圾文本。

### 3.2 时长与有语音强相关（最有用的发现）

| 素材时长 | 样本数 | 有语音 | 比例 |
|---|---|---|---|
| <5s | 170 | 61 | 35% |
| 5-10s | 84 | 57 | 67% |
| 10-15s | 26 | 26 | **100%** |
| 15-25s | 5 | 5 | **100%** |
| >25s | 1 | 1 | **100%** |

**10 秒是明确的分水岭。** 用 `--only-longer-than 10` 可以把算力砍掉一半以上，
而且不会漏掉任何有口播的素材。

规律本身很直觉：长镜头是博主对着镜头讲，短镜头是街景快速过场。

反过来说：**<5 秒的素材有三分之二是纯空镜**，不要对它们的转写结果抱期待。

### 3.3 模型档位

| 模型 | 大小 | 结论 |
|---|---|---|
| tiny | 75MB | **不可用**。短音频重复幻觉严重 |
| base | 145MB | 勉强。仍有重复，短片段基本无信息 |
| **small** | 480MB | **推荐**。10 秒以上片段直接出逐字稿 |
| medium | 1.5GB | 旁白是核心资产时可用 |
| large | 3GB | 性价比低，本场景不推荐 |

### 3.4 性能

| 项目 | 实测值 |
|---|---|
| 286 个素材抽帧 + 探测 | 约 3 分钟 |
| 286 个素材 MD5（10.59 GB） | 约 2 分钟 |
| 语音转写（small，2 线程，27.9 分钟音频） | 12 分 53 秒 |
| 模型加载（首次 / 缓存后） | 55s / 3-7s |
| 转写速度 | 约 2-13x 实时（取决于片段长短） |

转写比理论值慢，因为音频走管道时每条都要完整解码一遍，
短切片的**进程启动开销**占了大头。

## 四、工程上的坑

### 4.1 安全删除钩子会中断批量脚本

在批量转写循环里，音频临时文件复用了同一个路径，每轮 `os.remove()` 一次。
跑到第 50 次时脚本被中断：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50, ...}
EXIT=1
```

**同一个批次内批量删除超过 50 个文件会触发拦截。**

**解决方案：根本不要落临时文件。**
让 ffmpeg 直接把 PCM 输出到 stdout，读进内存交给模型：

```python
cmd = [FF, "-i", path, "-vn", "-f", "s16le", "-acodec", "pcm_s16le",
       "-ar", "16000", "-ac", "1", "-"]          # 输出到 stdout
p = subprocess.run(cmd, capture_output=True)
arr = np.frombuffer(p.stdout, np.int16).astype(np.float32) / 32768.0
segs, _ = model.transcribe(arr, ...)
```

既绕开了钩子，也省掉了磁盘 IO。同理，抽帧脚本用增量模式
（帧比源文件新就跳过）而不是每轮清空目录。

### 4.2 后台任务报 `completed` 但日志中途截断

上面那次中断，脚本明明是被杀掉的，但任务状态回报 `completed`，
日志只写到 `...20/286` 就断了。

**排查方法：不要信任务状态，去数真实产出文件的行数。**

### 4.3 PowerShell 5.1 重定向 Python stdout 会乱码

中文输出会变成 `绱犳潗渚﹀療鎶ュ憡` 这种。文件本身没问题，是显示层的问题。

**解决方案：让 Python 自己写 UTF-8 文件，再用 Read 读。**

### 4.4 用 `%` 格式化拼 HTML 会炸

CSS 里的 `100%`、`aspect-ratio` 会让 Python 的 `%` 格式化报
`ValueError: unsupported format character ';'`。

**解决方案：用 `.replace("__PLACEHOLDER__", html)` 占位符。**

### 4.5 文件数校验把回滚表算进去了

执行重命名时每批复核目录文件数，但回滚表 `_rename_done.tsv` 就写在素材目录里，
导致校验永远报 `6 -> 7 异常`。

**解决方案：计数时排除回滚表自身。**

## 五、视觉识别的效率设计

286 个素材逐个读帧图要读 286 次。改成一帧拼 4×4 = 16 格的联系表后：

```
286 帧 → 18 张联系表 → 读 18 次
```

**读图次数降低 94%，而且信息没有损失** —— 每格 400×225 足够判断"这是街景全景还是咖啡拉花特写"，
标签栏还带原文件名。

联系表设计的几个细节：
- 抽帧位置取 **50%**，避开片头黑场、对焦过程、相机 logo
- 缩略图**等比缩放后居中裁切**，不拉伸变形
- 每格下方留标签栏写 `#序号 原文件名`
- 自动找系统中文字体（微软雅黑 / 苹方 / Noto CJK / 文泉驿）
- 整图 1600×1020，JPEG quality 88 —— 再高对识别无帮助，只是徒增体积

## 六、整体结论

1. **视觉 + 语音双信号比任何单一信号都有用**。画面告诉你拍的是什么，声音告诉你讲的是什么。
   150/286 的口播率、74 条可用文案，这些信息从画面里读不出来。
2. **语音最有价值的输出不是"文本"，是"有没有文本"**。VAD 门禁可靠地区分了口播素材和空镜，
   这个二元信号在剪辑时的价值高于转写内容的准确率。
3. **不要用语音去命名**。短片段转写质量差，拿来命名会毁掉名字质量。画面仍是命名主依据。
4. **上游做扎实，下游省一遍**。素材入库时把画面、语音、时长都索引好，
   后面剪辑时就不用重新抽帧识别。
